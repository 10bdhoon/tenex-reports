1. 마스터플랜이 왜 필요한가

핵심: 지금 필요한 건 예쁜 소개자료가 아니라, TENOS 최종버전이 어디까지 만들어졌고 무엇이 비어있는지 한눈에 보이는 상위 지도다. 이 페이지가 있어야 하위 문서가 늘어나도 방향을 잃지 않는다.

4. 최종본 제작 방식

최종본은 한 번에 쓰는 문서가 아니라, 단계적으로 고정해나가는 구조다.

Phase A
구조 확정
  • 이름 고정
  • 모듈 고정
  • 조직 운영 구조 고정
  • 보고 경로 고정
  • 메모리 체계 고정
Phase B
흐름 확정
  • 이벤트 종류 정의
  • 라우팅 규칙
  • spawn 규칙
  • 승인 규칙
  • 실패 처리 규칙
Phase C
개발 범위 확정
  • V1 범위
  • V2 범위
  • V3 범위
  • 제외 기능
  • 첫 파일럿 도메인
Phase D
최종 통합
  • 조직도, 흐름도, 메모리, 로드맵을 한 페이지로 통합
  • 의사결정 가능한 최종본으로 마감

5. 실제로 최종본이 답해야 하는 질문

질문이 질문에 답하는 하위 문서
어떤 입력이 들어오면 누가 받나?TENOS Event Flow
실장은 뭘 하고 팀원은 뭘 안 하나?TENOS Naming / Policy
memory는 언제 검색되고 언제 저장되나?TENOS Memory
승인 필요한 작업은 어디서 멈추나?TENOS Policy
실패하면 누가 재시도하나?TENOS Runtime / Policy / Roadmap
OpenClaw를 대체하려면 무엇부터 구현하나?TENOS Engine / Roadmap

7. 한 줄 결론

최종버전은 새로 한 번에 쓰는 문서가 아니라, 마스터플랜을 상위 SSOT로 두고 하위 페이지들을 하나씩 완성한 뒤 마지막에 통합하는 방식으로 가야 한다.
