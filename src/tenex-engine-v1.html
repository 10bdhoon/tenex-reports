TENEX ENGINE V0.1 · OPENCLAW REPLACEMENT LAYER

테넥스 자체 엔진 아키텍처

이 페이지는 새 AI 조직도를 만드는 문서가 아니라, 이미 존재하는 테넥스 AI 조직 운영체계를 유지한 채 OpenClaw Gateway 레이어만 자체 엔진으로 치환하기 위한 시각화 초안이다. 즉, 조직 OS는 유지하고 런타임 커널만 바꾸는 설계다.

1. 먼저 답, 이거 가능한가?

가능하다. 다만 OpenClaw 전체를 범용 플랫폼으로 1:1 복제하는 게 아니라, 테넥스 전용 orchestration engine으로 범위를 좁혀야 한다. 즉 우리가 만들어야 하는 건 “새 OpenClaw”가 아니라 “테넥스 조직도를 돌리는 런타임”이다.

2. 안 바꾸는 것 vs 바꾸는 것

구분유지교체
조직 구조태훈 → 카리나 → 실장 → 팀원 spawn없음
운영 철학실장은 판단, 팀원은 실행, 카리나 최종 허브없음
메모리brain.db, MEMORY.md, daily memory, HEARTBEAT주입/기록 어댑터만 새로 구현
실행 인프라필요 없음OpenClaw Gateway, session orchestration, spawn layer
자동화기존 업무 자동화 철학cron 실행기와 이벤트 허브
보고 체계카리나 경유 보고, 사람 승인 후 자동화보고/승인 루프 구현체

3. 큰 그림, 우리가 만드는 건 엔진룸이다

조직 운영체계는 이미 정해져 있다. 이제 그 체계를 돌리는 런타임 레이어를 설계하는 단계다.

Layer 1
사람 입력
텔레그램, 슬랙, 웹훅, 정시 자동화 이벤트
  • 태훈 지시
  • 실장 보고
  • 크론 트리거
→
Layer 2
자체 엔진
라우팅, 세션 관리, 메모리 주입, 승인 루프
  • Router
  • Runtime Manager
  • Scheduler
→
Layer 3
리드 에이전트
카리나, 마실장, 개실장, 고실장, 콘실장
  • 판단
  • 기획
  • 검수
→
Layer 4
워커 에이전트
필요시 spawn, 실행 후 종료
  • 조사
  • 분석
  • 실행
→
Layer 5
보고 & 기억
카리나 통합, 태훈 보고, brain.db 저장
  • 결과 보고
  • 승인 요청
  • 기억 축적

4. 엔진 코어 모듈 8개

01 Router

Message Router

텔레그램, 슬랙, 웹훅, 내부 이벤트를 받아서 task envelope로 바꾸는 관문.

02 PM Layer

Orchestrator

카리나 직접 처리인지, 실장 위임인지, 팀원 spawn이 필요한지 판단하는 분배기.

03 Runtime

Agent Runtime Manager

리드 세션 유지, 워커 생성/종료, timeout, retry, fallback을 담당.

04 Memory

Memory Injector

brain.db 검색, MEMORY/HEARTBEAT 주입, 작업 후 결과 저장까지 담당.

05 State

Task State Tracker

현재 누가 무엇을 맡았는지, 어디까지 왔는지, 중간보고/완료 상태 추적.

06 Approval

Approval & Reporting Loop

사람 승인 게이트, 카리나 요약, 태훈 보고 경로를 강제한다.

07 Scheduler

Scheduler / Automation Runner

정시 실행, 리마인더, 수집, 이상값 감지와 같은 자동 이벤트 실행기.

08 Policy

Policy / Permission Layer

누가 어떤 명령을 내릴 수 있는지, 어떤 작업은 승인 필요한지 통제한다.

6. 단계별 실행 순서

1

SSOT 고정

조직도, 보고 경로, 승인 규칙, 메모리 소스, 자동화 범위를 먼저 확정한다.

  • 조직은 유지, 엔진만 교체
  • 무엇을 절대 보존할지 확정
2

이벤트 모델 정의

엔진이 다룰 사건 종류를 표준화해야 라우팅과 자동화가 단순해진다.

  • user_message
  • manager_task
  • worker_task
  • cron_tick
  • approval_required
  • task_complete
3

Lead / Worker 런타임 설계

리드는 상시 살아 있고, 워커는 spawn 후 소멸하는 구조를 구현한다.

  • persistent lead sessions
  • ephemeral worker runs
  • timeout / retry / fallback
4

메모리 주입 규칙 정의

작업 전 검색, 작업 중 상태 추적, 작업 후 저장 형식을 고정한다.

  • brain.db 검색 규칙
  • MEMORY/HEARTBEAT 포함 조건
  • 결과 저장 포맷
5

보고 / 승인 루프 구현

고객 대면/배포/민감 변경은 승인 게이트를 통과하게 만든다.

  • 실장 → 카리나 → 태훈
  • 사람 승인 후 자동화
6

한 도메인으로 파일럿

전체를 한 번에 올리지 말고, 반복성이 높고 성과 측정 쉬운 영역부터 검증한다.

  • 추천: 마케팅 또는 CRM
  • 다음 후보: CS, 개발 운영

7. 현실적인 리스크

리스크 1

세션 관리가 제일 어렵다

겉으로 쉬워 보여도 가장 복잡한 부분은 runtime과 context continuity다.

리스크 2

메모리 오염 가능성

관련 없는 기억을 잘못 주입하면 답변 질이 오히려 무너진다.

리스크 3

보고 체계 붕괴

카리나 경유 규칙이 깨지면 AI들이 각자 떠드는 구조가 된다.

8. 최종 결론

핵심 우리가 만드는 건 새로운 AI 조직이 아니라, 기존 테넥스 AI 조직도를 살리는 자체 런타임이다.

즉 조직 OS는 이미 있다. 이제 할 일은 OpenClaw를 걷어내고, 그 OS를 돌릴 Tenex Engine의 커널을 만드는 것이다.
