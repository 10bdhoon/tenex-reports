SOUL.md 성격 & 톤
~/.openclaw/workspace/SOUL.md
카리나의 정체성. 결론부터, 실무 중심, 반말, 이모지 최소화. 거울/외장RAM/시스템빌더 역할

USER.md + MEMORY.md
~/.openclaw/workspace/MEMORY.md (22KB, 트런케이션 위험)
태훈 개인정보 + 카리나의 장기 기억 (사업 현황, 제품, 전략, 개인 컨텍스트)

memory/YYYY-MM-DD.md
~/.openclaw/workspace/memory/ (일별 대화 일기)
오늘/어제 대화 기록. 컴팩션 후에도 살아있는 원본 맥락

HEARTBEAT.md + TOOLS.md

BOOTSTRAP 핵심 규칙 6가지
🔴 규칙 1
개발 = 에이전트팀에게 위임
카리나는 코드를 직접 짜지 않는다. 기획서 작성 → sessions_spawn으로 에이전트에게 전달 → 결과 검수. PM 역할만.
🟠 규칙 2
슬랙 = 스레드 없이 본문에 직접
슬랙 메시지는 스레드 달지 않고 본문에 깔끔하게. 불렛포인트, 이모지 최소화.
🟡 규칙 3
추측 금지 — 모르면 매뉴얼 읽기
불확실하면 솔직히 "모르겠습니다". 추측은 "추측:" 명시. AGENTS.md → TOOLS.md → MEMORY.md → LEARNINGS.md 순으로 확인.
🟢 규칙 4
프로젝트 = 체크리스트 먼저
새 프로젝트 시작 전 TASK.md 또는 TODO 작성. 진행 상황 실시간 업데이트. 완료 시 CHANGELOG.md 기록.
🔵 규칙 5
실수 = 즉시 LEARNINGS.md 기록
실수 발생 즉시 날짜/원인/해결/교훈 형식으로 기록. 같은 실수 반복 금지. 주간 리뷰로 패턴 개선.
🟣 규칙 6
브라우저 자동화 = 스냅샷 먼저
브라우저 자동화 전 snapshot으로 페이지 구조 파악. 요소 ref/클릭 경로 문서화. 테스트 후 스크립트 작성.

해결책: 중요한 대화는 즉시 memory/일기 + brain.db에 저장. MEMORY.md는 항상 핵심만 유지 (현재 22KB → 목표 10KB 이하).

⚙️ OpenClaw 작동 원리

태훈의 AI 파트너 시스템이 어떻게 동작하는지 — 완전 해부

📨 메시지 처리 흐름 (1회 대화 기준)

1

텔레그램 메시지 수신

태훈이 메시지 전송 → 텔레그램 서버 → OpenClaw Gateway (맥미니 상시 가동)
각 채팅창(chat_id)별로 구분됨

↓
2

세션 확인

chat_id 기반으로 기존 세션 조회. 세션이 있으면 이전 대화 이어서 진행. 새 그룹이면 신규 세션 생성.
sessionKey: agent:main:telegram:group:{chat_id}

↓
3

시스템 프롬프트 조립

매 호출마다 다음을 조립해서 AI에게 전달:

• SOUL.md (카리나 성격/역할) → 항상 포함
• USER.md (태훈 정보) → 항상 포함
• MEMORY.md (장기기억) → 항상 포함 (22,973자 → 20,000자 제한으로 잘림)
• AGENTS.md, BOOTSTRAP.md 등 → 항상 포함
• 대화 히스토리 → 세션에 쌓인 이전 대화들

↓
4

Claude API 호출 (Anthropic)

조립된 시스템 프롬프트 + 대화 히스토리 + 새 메시지를 Claude에게 전달
모델: claude-sonnet-4-6 | 컨텍스트 윈도우: 200,000 토큰

↓
5

도구 실행 (Tool Use)

AI가 필요한 경우 도구 호출 (파일 읽기, exec 실행, 웹 검색 등)
도구 결과를 다시 AI에게 전달 → 최종 응답 생성

↓
6

텔레그램으로 응답 전송

AI 응답 → OpenClaw Gateway → 텔레그램 API → 해당 채팅창에 전달

🔄 세션 구조 — 대화창이 곧 팀원

현재 상태 (50% 최적화)

  • 모든 창이 동일한 시스템 프롬프트
  • 각 창이 서로 뭐 하는지 모름
  • brain.db 자동 pull 안 됨
  • MEMORY.md 22,973자 → 잘림
  • 세션 재시작 = 메모리 리셋

이상적 상태 (목표)

  • 창별 전용 역할/지식 주입
  • brain.db로 창간 공유 메모리
  • 세션 시작 시 관련 맥락 자동 로드
  • MEMORY.md → 채널별 핵심 5,000자
  • 컨텍스트 압축/롤링 윈도우

❓ 자주 묻는 것들

Q. 세션 종료를 한 적이 없는데 각 창 세션이 계속 유지되나?
✅ 유지됨. OpenClaw는 chat_id 기준으로 세션을 관리. 종료 안 하면 대화 히스토리가 계속 쌓임. 단, 컨텍스트 압축(컴팩션)이 일어나면 오래된 대화가 요약으로 대체됨.
Q. 그룹챗에서 /restart 권한이 없다고 뜨는 이유?
OpenClaw의 그룹 세션은 명령어 권한이 DM과 다르게 설정돼 있어. /restart, /reset 같은 명령은 DM(메인 세션)에서만 허용됨. 그룹 채팅창에서 세션을 리셋하려면 openclaw.json에서 관리자 권한 추가가 필요함.
Q. 10개 창 = 10개 팀, 너무 과한가?
아니야. 오히려 좋은 구조야. 단, 지금은 "같은 직원이 10개 책상에 앉아서 일하는 것"에 가까워. 각 책상에서 어떤 일을 해야 하는지 역할을 명확히 정의하고, 공유 메모리(brain.db)로 소통하면 진짜 10개 팀이 됨.
Q. MEMORY.md를 경량화하면 맥락을 잃지 않나?
brain.db에 원본이 다 있으니 잃지 않아. MEMORY.md는 "매번 AI에게 주입하는 것"이라 핵심만 넣는 게 맞음. 세부 내역은 필요할 때 brain.db에서 검색해서 가져오는 구조로 분리.

업무 지시 방식 — 맞는 방법 vs 틀린 방법
❌ 지금 하고 있는 방식
"이거 코드 짜줘" → 카리나가 직접 실행
"HTML 만들어줘" → 카리나가 write 툴로 직접 작성
"스크립트 수정해줘" → 카리나가 edit 툴로 직접 수정
결과: 카리나 컨텍스트 낭비, 속도 느림, 병렬처리 불가
✅ 맞는 방식
"이거 만들어" → 카리나가 TASK.md 작성 → 텐동에게 전달
기획 의도 + 요구사항 + 컨텍스트를 TASK.md에 담음
텐동이 서브에이전트 병렬로 돌림 (훨씬 빠름)
카리나는 결과 검수 + 태훈에게 보고만
실전 예시
예시 1 — 대시보드
매출 대시보드 새 탭 추가
태훈: "광고 흐름 탭 추가해줘" →
카리나: TASK.md 작성 (API 스펙, 디자인 요구사항, brain.db 컨텍스트) →
텐동: 프론트+백엔드 병렬 실행 →
카리나: QA 후 태훈에게 링크 전달
예시 2 — 자동화
CRM 문자 발송 자동화
태훈: "ES-808 출고 당일 문자 자동화" →
카리나: 카페24 API 스펙 + 문자 내용 + 발송 조건 TASK.md 작성 →
텐동: 백엔드 에이전트에게 스크립트 작성 위임 →
카리나: 테스트 실행 + launchd 등록
예시 3 — 페이지
브랜드 디자인 시스템 HTML
태훈: "디자인 시스템 정리해서 배포해" →
카리나: 컨텐츠 기획 + 디자인 방향 TASK.md →
텐동: 프론트엔드 에이전트에게 위임 →
카리나: Vercel 배포 + 링크 전달
예시 4 — 앱
키네메디칼 앱 MVP
태훈: "앱 기획 잡고 개발 시작해" →
카리나: 기능 명세서 + 화면 흐름 + 기술 스택 TASK.md →
텐동: 프론트+백엔드 병렬 개발 →
카리나: 주 단위 진행상황 보고
